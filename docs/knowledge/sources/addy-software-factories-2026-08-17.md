## 一、核心定义

### 1.1 三层架构：Loop → Harness → Factory

```
Loop（循环）     = 一个代理重复做一件事：收集上下文 → 执行动作 → 检查结果 → 重复
Harness（脚手架）= 循环的围墙：沙箱、工具、记忆、完成门控
Factory（工厂）  = 大规模运行的多个受控循环，通过工作队列输入，通过审查门控输出到生产
```

**关键区别**：Factory 不是一个更大的 Agent，而是一个**由循环组成的组织架构图**。

### 1.2 Light Factory vs Dark Factory

| 概念 | Light Factory（明亮工厂） | Dark Factory（黑暗工厂） |
|------|-------------------------|-------------------------|
| 定义 | 人类在循环中参与（审查） | 代理自主范围、构建、发布代码 |
| 核心特征 | 人类读取产出后才发布 | 代码被发布时没有人类阅读过 |
| 借鉴来源 | 制造业的传统工厂 | 制造业的关灯工厂（FANUC 2001, Xiaomi 2024） |
| 风险 | 低吞吐量瓶颈 | 理解债务积累（Comprehension Debt） |
| 适用场景 | 高风险变更 | 低风险、可机械验证的变更 |

### 1.3 "Dark" 的精确含义

**"dark" 是一个物理主张**，不是态度或侮辱。在制造业，关灯工厂只因为设备不需要照明。在软件，"地板"是 diff——写、审、发的人都不在了，只剩机器验证的 diff。

## 二、核心框架

### 2.1 工厂 wiring diagram（接线图）

```
Intent（工程领导力愿景） + Signals（事故、用户请求）
           ↓
      [工作队列]
           ↓
      [Harness 构建]  ← 代理在此工作
           ↓
      [自动化检查]  ← CI、测试、静态分析、扫描（几乎零成本）
           ↓
   [Review Gate]  ← 唯一昂贵的环节：人类判断
           ↓
      [部署] → [监控] → 反馈回 Signals
```

**关键洞察**：工厂中几乎每个环节的成本趋近于零（生成、测试、扫描），**唯一无法规模化的是 Review Gate（审查门控）**——那就是"判断"。

### 2.2 Back Pressure（背压原则）⭐

> "你只能给循环赋予你能**廉价且可靠地验证**的自主权，多一寸都不行。"

- 验证，而非生成，是工厂的真正约束
- 无限生成能力与有限人类注意力之间存在永久张力
- 问题的核心不是高产出量，而是**低质量 PR 的过剩**
- 当验证瓶颈未拓宽时，加速生成只会加深堆积

### 2.3 代理步数的经验法则

**Dex Horthy 的观察**：代理在 3-10 步内保持稳定，超过 20 步开始失去线索。原因是**上下文累积**。

- 短循环更容易验证
- 长循环在角落隐藏错误
- 短循环更容易"赢得"黑暗（全自动）资格

## 三、Harness Engineering Is Not Enough

### 3.1 核心论点

Harness Engineering 本身不足以维持代码库质量。原因是：

1. **Comprehension Debt（理解债务）**是代码存在量与人类理解量之间的不断扩大的差距
2. Dark Factory 不偿还理解债务，而是以最大速度积累它（测试全程绿灯）
3. 模型在小型变更上表现良好，但在**复杂的棕地系统**（brownfield）上面临不可逾越的障碍

### 3.2 Dex 的实际经验

运行完全自动化的代码工厂约 4 个月，期间无人类查看代码。发现两个矛盾指标：
- **最大化 token 利用率**（被当作进步的指标）
- **最小化人类理解量**（被默默牺牲的指标）

最终后果：需要痛苦的**人工调试**来定位问题。

### 3.3 Dark Factory 的讽刺

> "Dark factory 真正擅长的是在测试保持绿灯的同时燃烧完好的代码。最终的清算不会是戏剧性的'全面崩溃'时刻——它会是**安静的，且迟到的**。"

## 四、Turning the Lights Back On（重新开灯）

### 4.1 Light Factory 的设计

Light Factory 不只是在末尾加审查，而是**将人类判断点前移到产品、设计和架构阶段**。

**好处**：
- 将 2000 行代码的审查变成 200 行计划的快速审阅
- 在决策构建之前就能审查它
- 在成本复合之前就有人参与

### 4.2 安全网 = 乏味的架构实践

架构现在有了**第二份工作**：作为代理错误的廉价且难以伪造的安全网：

- 好的类型和方法签名 → 编译器捕获错误
- 测试接缝 → 行为可观察
- 代码布局清晰 → 下一个读者（人或模型）能找到关注点
- 短而清晰的调用栈
- 良好的组件边界 → 变更不会有大爆炸半径
- 依赖注入 → 可替换

> "安全网必须在模型之外，因为模型不会自己提供它。"

### 4.3 Claude Code 和 Codex 的局限

被强化训练在**自己的 harness 和工具**上，擅长工具和惯例，但不擅长**长期可维护性**。有意识的架构是捕获该债务的工具。

## 五、What Earns a Loop the Dark（什么让循环赢得黑暗资格）

一个循环获得全自动状态的条件：
1. ✅ 检查廉价
2. ✅ 高频运行
3. ✅ 依赖难以伪造的东西（type gates、property tests、绿/红预言机）

**需要人类审查的循环**：
- ❌ 错误代价高昂
- ❌ 只有人类能捕获
- ❌ 大爆炸半径
- ❌ 影响一年的工作

**Dex 的实用模式**：夜间的 GitHub Actions cron 每晚修复一个反模式（lint 违规或不必要的可选 prop），提交并开一个小 PR，团队醒来时代码库变得稍好一些。

## 六、Loops, Graphs or State Machines?（循环、图还是状态机？）

### 6.1 从循环回归图

Agent 的"自主性"实际上是在一个特定图内的节点之间行走。真正的自由度被限制在节点内部。

> "这个问题几乎是在承认，我们一直都需要流程图。"

### 6.2 图 vs 循环的实践对比

**纯循环方式**：坐下来想→改代码→跑测试→看结果→循环回来。整个旅程边走边决定。

**图方式**：先映射应该发生什么：
```
复现 bug → 找原因 → 试修复 → 跑测试 → 失败→回修复 | 通过→审查 → 通过→完成
```

Agent 在每个节点内仍然聪明，只是不能偏离批准的路径。

**图的吸引力**：它是**用图画的背压**。放弃一些自由，获得强制检查和可读的失败点。

### 6.3 行业趋势

- LangGraph、LlamaIndex Workflows
- Jerry Liu 的混合 workflow-graph-over-agents
- David Khourshid 的状态机和 actor model

> "大多数所谓的 Agent 实际上并不太有'代理性'：**大部分是确定性代码，在正确位置撒上一些 LLM 步骤**。"

## 七、与已有知识体系的关系

### 7.1 对 Loop Engineering 的扩展
- Loop Engineering 定义了五大构件，Software Factories 是**循环的大规模组织**
- 从单个循环的设计上升到工厂的架构设计

### 7.2 对 Harness Engineering 的补充
- **Harness Engineering Is Not Enough** 是对 Harness Engineering 的重要警示
- 仅有 Harness 不够，还需要工厂级别的审查门控和人类判断

### 7.3 新概念清单
| 概念 | 定义 | 关联 |
|------|------|------|
| Light/Dark Factory | 明亮/黑暗工厂 | Factory 架构模式 |
| Back Pressure | 背压原则 | 验证是瓶颈 |
| Review Gate | 审查门控 | 工厂唯一昂贵环节 |
| Comprehension Debt in Factory | 工厂中的理解债务 | 认知投降 |
| Loop/Graph/State Machine | 循环 vs 图 vs 状态机 | Agent 执行模式 |
