## 一、上次截断内容补充

### 1.1 通过已批准域的数据外泄（完整细节）

**攻击场景**：
- 恶意文件放在用户的挂载 workspace 中
- 文件携带隐藏指令和攻击者控制的 API key
- Claude 读取 workspace 其他文件，使用攻击者的 key 调用 Anthropic Files API
- 出口代理检查目标地址为 api.anthropic.com → 放行
- 文件被上传到攻击者的 Anthropic 账户
- **沙盒完美工作，但数据仍然被外泄**

**关键范式转变**：
```
旧概念：允许列表 = 目标过滤器
  "这些域名可以访问"

新概念：允许列表 = 能力授予
  "该域名上的每个可达功能都成为攻击面"
  允许 api.anthropic.com = 允许向任意 Anthropic 账户上传文件
```

**修复方案 - 防御性中间人代理**：
- VM 内部的 MITM 代理拦截发往 API 的流量
- 只允许携带 VM 自身配置的 session token 的请求通过
- 攻击者嵌入的 key 被代理拒绝
- 同时阻止启用 server-side fetch 的 header
- 代理放在 VM 内部（而非服务器端），因为只有 VM 知道来源

**安全原则**：
> "你自建的软件通常是最薄弱的环节。Hypervisor、seccomp、gVisor 都可靠；我们自建的允许列表代理是失败的组件。"

### 1.2 VM 隔离的副作用：EDR 不可见

**问题**：
- 企业安全团队问："为什么我们的 EDR 看不到内部？"
- 答案：保持 Claude 受限的同样隔离也阻止了宿主端点检测和响应（EDR）
- 从 EDR 角度看，Claude Cowork 只是一个不透明的 hypervisor 进程

**核心矛盾**：
```
隔离强度 ↑ → 可见性 ↓

安全团队需要端点可见性来满足合规要求
但隔离设计天然阻止了这种可见性
```

**当前缓解措施**：
- 使用拉取式 OTLP 导出，让管理员事后检索事件日志
- 但这不是实时监控
- 建议：如果你在构建类似系统，尽早为此预留讨论空间

### 1.3 信任代理读取的内容

**MCP 安全的双重风险**：
```
外部资源 = 两个风险同时存在：
1. 代码执行风险（传统供应链安全）
2. Prompt 注入向量（新型风险）

传统依赖审计（锁定版本、验证签名、审查源码）
  → 只解决了第一个风险
  → 完全遗漏了第二个风险
```

**远程 vs 本地工具的关键区别**：
```
本地安装的工具：可审计
  - 可以读代码
  - 可以锁定版本
  - 确保不会在运行时变更

远程工具（托管 MCP 服务器、云连接器）：不可控
  - 可以在审批后随时变更行为
  - 安装时的信任决策可能已经过时
  → 应视为不受信任，先对假数据运行
```

**工具输出即攻击面**：
- 即使工具本身可信，其输出仍是攻击面
- GitHub README 例子：被审计的连接器 ≠ 被审计的数据
- 在 Claude Code 和 Claude Cowork 中，工具调用通过代理路由：
  - 执行网络和文件策略
  - 在返回值进入模型上下文前进行检查
  - 检查分类器可以是小而快的模型，无需使用推理模型

**关键洞察**：
> "一旦被污染的工具返回引导代理外泄数据，日志只显示一次成功、已授权的 API 调用。没有事后信号可以追溯。"

### 1.4 前瞻性安全挑战

**1. 持久性内存中毒（Persistent Memory Poisoning）**：
```
风险：代理跨会话持久化的上下文越来越多
  - 产品记忆
  - CLAUDE.md 文件
  - 挂载的 workspace
  - 定时和长时间运行代理的状态目录

威胁：注入这些持久存储的内容会在每次代理启动时被重新加载
  → 经典后渗透（post-exploitation）中的持久化机制

防御方向：会话启动时的良好分类器将变得必要
```

**2. 多代理信任升级（Multi-Agent Trust Escalation）**：
```
优势面：
  - 子代理可以隔离不受信任的内容
  - 返回结构化事实而非原始文本给主代理

风险面：
  - 如果子代理输出被视为比原始工具结果更高信任
    （因为"这是我们自己代理的输出"）
  - → 新的 Prompt 注入向量

核心权衡：在分配不同信任级别 vs 面临信任升级漏洞之间
```

**3. 代理身份（Agent Identity）**：
```
Claude Cowork 的方案：
  - 凭证留在宿主 keychain
  - VM 获取每会话的受限 token
  - token 可独立于用户凭证撤销

更广泛的开放问题：
  - 代理应拥有自己的主体身份？
  - 还是作为用户扩展继承用户权限？
  - 答案可能是两者的混合
```

### 1.7 四个核心安全原则总结

**原则 1：环境层优先，模型层辅助**
> "设计包含在环境层，然后通过模型层引导行为。两次教训最深的入侵（员工钓鱼和第三方允许列表泄露）都是出口问题——数据通过许可路径离开。模型层无能为力。确定性边界是所有概率性防御失效时的最后防线。"

**原则 2：隔离强度匹配用户监督能力**
> "能读 bash 的开发者和不能读的知识工作者不在同一威胁模型下。用户能否评估代理即将执行的操作应帮助确定包含策略。两个方向都答错——对专家摩擦过大，对非专家信任过多——都是失败。"

**原则 3：警惕自建组件**
> "经过对抗性考验的 hypervisor、系统调用过滤器和容器运行时比你能构建的任何东西都更可靠。在本文描述的每个部署中，标准原语都正常工作，而我们自己构建的部分暴露了缺陷。"

**原则 4：代理虽新，系统级交互不新**
> "代理可能是一种新类别的软件，但它们的系统级交互并不新。它们仍然读取文件、打开 socket、生成进程。这使得使用成熟工具进行包含成为一种至关重要的可行防御。"

## 二、审视性补充：与 Harness Engineering 的关联

### 2.1 Containment 作为 Harness 的安全层

Anthropic 的三种隔离模式与 Harness Engineering 的关系：
```
Harness 设计不仅要考虑：
  ✅ 功能性（工具、上下文、反馈回路）
  ✅ 可靠性（错误处理、恢复路径）
  ✅ 效率性（上下文管理、资源优化）

还要考虑：
  🆕 安全性（包含、出口控制、注入防御）

安全不是附加层，而是 Harness 设计的一等公民
```

### 2.2 对 Loop Engineering 的安全启示

```
Loop 运行中代理可以：
  ✅ 打开 PR
  ✅ 链接 ticket
  ✅ ping 频道
  ⚠️ 但如果 loop 中的代理被注入？
     → 所有这些自动化动作都成为攻击面

启示：Loop Engineering 必须内建安全约束
  - 出口白名单
  - 操作范围限制
  - 状态文件的完整性保护（防止持久化内存中毒）
```

### 2.3 对本项目的具体启示

1. **安全原则应纳入 Harness 设计**：feature_list.json 中的安全相关特性应参考 Anthropic 的经验
2. **工具输出检查**：所有 MCP 工具的返回值应在进入模型上下文前进行检查
3. **持久化存储安全**：AGENTS.md、状态文件等持久化内容应考虑注入风险
4. **子代理信任模型**：多代理系统中需要明确的信任边界和级别分配
